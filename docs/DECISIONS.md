# DECISIONS · the places in the spec where I made the call (one line each, with the reason)

- D01 The MCP server is hand-written stdio JSON-RPC (initialize / tools/list / tools/call / ping), not the `mcp` package: the protocol here is four methods, and that is one fewer dependency to drift. First contact talks to it with the same client code.
- D02 A proposal's `base` = the target file's git blob short hash (first 8 chars, same value as `git hash-object`, computed locally, no subprocess); a new file is written `base: new`.
- D03 A proposal's 「改成什么」 must hold one fenced code block = the whole new file (add / replace), or have `retire` on its first line (retire = move to retired/ alongside). A prose-only proposal cannot be landed by a machine, and `plug apply` refuses it and says so.
- D04 An approved proposal moves to `proposals/applied/` (the spec only named pending / rejected / tools; leaving an approved one in pending is wrong and deleting it breaks the trail).
- D05 One FTS5 table is the only retrieval table; two more, `files` (file hashes, for incremental builds) and `meta` (the alias map as JSON, build time, versions), are bookkeeping and are not searched.
- D06 Cleaned-transcript format (the spec had no sample): six `Key: value` header lines + one `====` line + paragraphs starting with `[m:ss]` or `[¶n]`. When one doc id has both raw and clean, only clean is indexed; anchor sentences are grepped in both.
- D07 Doc id order: frontmatter `id` → header `BVID:` / `ID:` → filename stem; series = the prefix before the first separator (｜ | · — - ： :) in the title, verbatim.
- D08 check is split into check.py (findings + report), numbers.py (sync rate) and contact.py (first contact), with eval.py alongside: <=250 lines per file matters more than landing on exactly eight files.
- D09 Agreement is decided as: chosen, normalised, equals verdict, or starts with one of the owner's assent words (同意 / 同 / 按它). Everything else is a disagreement. Who was right afterwards is read from the outcome markers 它对 / 我对 / 说不清.
- D10 "Blind-valid" is verified against git history: in the version where the file was first committed, verdict was set and chosen was empty. Records not yet committed do not count towards the denominator.
- D11 Material shelf life: a material's frontmatter `date` is required, `kind` optional; the number of days comes from that equipment's `ttl_days: {kind: N, default: N}` in plug.yaml (90 by default).
- D12 "New" in "new entry with <3 inbound links" = first committed within 30 days (not yet committed also counts as new).
- D13 `[?]` reconciliation: an equipment may declare `unreviewed: N` in plug.yaml; a mismatch with the actual count is a WARNING. Without the declaration nothing is checked.
- D14 Protected paths default to self/RULES.md · self/facts/** · tools/** (minus **/corpus/**); materials/ is included (the spec says append-only and the writer is the owner). Overridable in plug.yaml `protected:`.
- D15 "Hook has not fired recently" threshold: 30 days, absence included.
- D16 "A warning / diagnostic playbook giving actions aimed at the other party" is a heuristic: a line in the 动作 or 练习 section starting with 让对方 / 叫对方 / 要求对方 / 告诉对方 / 向对方.
- D17 The compaction pin is two-stage: PreCompact computes it, writes `.kb/pin.md` and prints it; SessionStart(compact) runs the same script with `--emit` and hands it back as additionalContext — PreCompact's stdout is not guaranteed to reach the context.
- D18 Mirroring a manual = copying SKILL.md into each pilot's skills directory from plug.yaml (default .claude/skills · .agents/skills), not a directory link; the link approach is documented in pilots/codex instead.
- D19 index.md / INDEX.md generated by index are not git-added by pre-commit; when generated files get committed is the owner's call.
- D20 The generic mount point: `checks/*.py` runs as a subprocess, 60 s limit, with PLUG_ROOT / PLUG_TOOL in the environment; one WARNING per stdout line, exit code 2 = ERROR.
- D21 `file#Lstart-Lend` in a search row uses 1-based line numbers (matching Read and sed); a cleaned transcript's paragraphs carry `[m:ss]` or `[¶n]` as their position.
- D22 Query construction: split on whitespace and punctuation; a Chinese run of <=4 characters becomes a bigram phrase ("责任 任转 转移"), longer runs use jieba words of >=2 characters; latin words are lowercased; everything is OR-ed. Alias expansion uses the same rule.
- D23 The deny template uses `Edit()` only (officially, an Edit rule covers every built-in file-editing tool including Write; a `Write()` rule is never checked); `Read(self/RULES.md)` is never denied, or the pilot cannot read the rules; `Read()` is used only on `.kb/hooks/**`, the stamps the pilot should neither read nor change.
- D24 First contact step ④: pre-commit really runs (PLUG_STAGED stands in for the git index), while deny is only verified by looking for `Edit(…self/RULES.md)` in the settings file — the machine does not start Claude Code itself. Whether deny really blocks under bypass is MANUAL item C1.2.
- D25 "New entry with <3 inbound links" and "orphan entry" only count dictionary entries (concept / method); playbooks are found through INDEX.md, not through links.
- D26 Index freshness is not judged by mtime (two edits in one second are indistinguishable) but by comparing file hashes in the `files` table.
- D27 The corpus is chunked per paragraph (blank-line separated; a cleaned transcript is one paragraph per line with `[m:ss]`), and a paragraph over 800 characters is cut into 600/100 windows; entries / records / materials are one chunk per page (BM25 favours short chunks, so splitting by section would let `## 注` outrank `## 定义`).
- D28 Proposals are indexed into their own scope, `proposals` (invisible to the default `tools` scope, visible with scope=all); otherwise a proposal containing a whole file would outrank the dictionary entry it is about.
- D29 `plug apply` runs `plug index` once more after landing: the proposal has left pending and the playbook directory must stop listing it.
- D30 "Cites earlier records": the 依据 section containing 上次 or `records/` counts as that one of the four elements; the very first record saying 无类似记录 also counts as complete.
- D31 Laying out the one-page report moved from check.py to report.py (check.py was over the hard 250-line limit; check only finds problems, report only formats). The package is 14 files and roughly 1,700 lines, of which about 140 are the mandated header comments; the excess over "~1,000 (<= ~1,300)" is mostly check's ERROR and WARNING classes at 3–6 lines each, and it has not been squeezed further — squeezing makes it unreadable.
- D32 Generated files index.md · playbooks/INDEX.md · the numbers page are committed in the example equipment (they show what the machine produces); `.kb/` and the mirrored skills directories are gitignored.
- D33 Every write uses newline="\n" (on Windows write_text turns LF into CRLF, which changes the base short hash — acceptance item C2.4 is how that was found).
- D34 `plug init`: the hook goes into .git/hooks/pre-commit (git pull leaves it alone; on Windows git runs it with sh; if the owner set core.hooksPath it goes there; anyone else's pre-commit is renamed aside). Claude Code's deny rules and hooks both go into .claude/settings.json (Claude Code does not read .claude/hooks.json). .mcp.json and .codex/config.toml use the current interpreter's absolute path plus `-m entryplug.cli --root <root> mcp`, so nothing depends on `plug` being on PATH. Codex gets a repo-level .codex/hooks.json (the user-level ~/.codex is left alone for the owner to merge). Generated pilot files carry this machine's absolute paths and belong to this machine.
- D35 `search` returning 0/0 no longer stays mute: the tail line names the scope (the default `tools` covers dictionary · playbooks · records; the corpus needs scope=corpus) and when the index was built. With no index the CLI says "run plug index first" and exits 1, and MCP returns isError text. The CLI and MCP were always the same function with the same default scope.
- D36 `plug apply` is the owner's move. If any agent-environment marker is set (CLAUDECODE, CLAUDE_CODE_ENTRYPOINT, CODEX_SANDBOX, … — presence only, values are not inspected) it refuses and prints the owner's two lines. `--dry-run` is allowed for everyone. The escape hatch is `--owner` (or `PLUG_OWNER=1`), because Claude Code's `!` prefix runs in the same environment as the agent's Bash tool, so no environment check can tell an owner keystroke from an agent tool call. That makes this a speed bump with an audit trail, exactly like "do not set KB_APPROVE by hand" — the airtight layer is still pre-commit.
- D37 `.plug-off` at the content repo root turns off only the soft gates: the sortie lock, the compaction pin and the record reminder pass straight through. Deny rules and pre-commit are untouched, so what is protected stays protected in either mode. `plug status` always reports which mode you are in.
- D38 Two free zones, `work/<equipment>/` (products) and `workshop/<equipment>/` (building new equipment): never protected, never walked, never indexed. On top of that, anything under `tools/` belonging to no equipment registered in plug.yaml is not protected either — so deny generation and pre-commit only ever cover `self/` and the registered equipment. Registering an equipment is what makes it protected.
- D39 Equipment = skill: `plug init --link-skills` copies (rather than symlinks) each SKILL.md into the user-level skills directory, so the content repo's absolute path can be stamped into the copy — that stamp is what tells the equipment products belong in `<root>/work/<equipment>/`. Symlinks would carry no stamp and need privileges on Windows. It is a manual trigger, and no user-level MCP server is ever registered: outside the content repo you get the manual, not the Base. `disable-model-invocation: true` in a manual's frontmatter rides along in the copy and also flips Codex's `allow_implicit_invocation` to false.
- D40 The record reminder is a Stop hook and is reminder-level: it never blocks, always exits 0, and emits at most one `systemMessage`. When the session began is taken from the transcript file's creation time, else the previous Stop stamp, else an 8-hour window (PLUG_RECORD_WINDOW). `.plug-off` silences it. This supersedes the earlier "there is no Stop hook" rule, which was written to forbid a *blocking* one.
- D41 `plug status` prints six counted checks (index · Base · AT-Field · berserk lock · sortie lock · equipment bay) plus one informational line for `.plug-off`, which is not counted. The sync rate is simply passed/total. The exit code is nonzero only when the index layer itself is unusable — a degraded lock is loud but does not stop a session. The closing line names the content repo's own directory rather than a hardcoded unit name, so the public machine repo holds nobody's repo name.
- D42 The machine speaks English: comments, docstrings, CLI help and error text, the reports, the README and docs. Content stays in the language it was written in — the Sunzi corpus, dictionary, playbooks and materials, the example Base, and the owner's own words. Shape v1's on-disk vocabulary is data, not prose, and does not move: the section headings (依据 / 最强反证 / 什么会改判 / 改成什么 / 为什么 / 定义 / 观察 / 关系), the markers `[?]` and `[未锚]`, the assent words and the outcome markers, `plug.yaml: language`, and the numbers page's default path `self/数字.md`.
- D43 The owner's copy-paste block lives in three places — the map templates, the footer of every proposal file (check warns with code `footer` when a pending one lacks it), and the pending-proposals section of `plug check`'s report, which prints the real path so the owner can copy it straight out — and its wording is generated in exactly one place, `apply.owner_lines()`. It has two forms, not one: a terminal form (`plug apply <p>` / `--reject`) and a chat form carrying `--owner`. Printing a bare `!`-prefixed approval would hand the owner a command that D36's own gate refuses, since `!` runs in the pilot's environment; `tests/test_apply.py` scans every tracked file for exactly that mistake. `--dry-run` needs no flag anywhere.
- D44 plug.yaml gains an optional `exclude:` glob list that `walk()` honours, so a content repo can keep something out of the index without moving it and without unprotecting it. It is deliberately a visibility switch only — `is_protected` never consults it, so an excluded file is still refused by pre-commit — because the alternative (making one list do both jobs) would let "stop indexing this" quietly mean "stop protecting this". Added for a real content repo whose fact sheet must never become retrievable.
- D45 plug.yaml gains `corpus:` — a list of {path, tool, sub} entries mounting corpus directories that do not live under `tools/<equipment>/corpus/`. walk() hardcoded that layout, so a content repo keeping one shared corpus at its root could not be indexed at all without moving the files, and moving a thousand transcripts to satisfy a directory convention is the tail wagging the dog. `tool` is a label on the rows, `sub` keeps the clean-beats-raw rule, and a declared directory that is not there is a `corpus_path` WARNING rather than a silent skip.
- D46 plug.yaml gains `protect:` — extra globs for the berserk lock — and it is deliberately read by **both** layers: `init.deny_rules` emits a deny rule for each entry and `config.is_protected` hands the same list to pre-commit. The alternative, letting the owner extend one layer only, produces the exact asymmetry found in unit-01, where an equipment's kit directory was refused at commit time but freely editable by the pilot — the worst of both, since the work is lost rather than prevented. `protect:` cannot override the two hard exemptions (free zones, unregistered tools/), because those are the machine's promise that products and drafts stay writable.
- D47 `plug index` compares the file hash **before** generating rows, so an unchanged file is never tokenised again and its chunk count is read back from the table. Tokenising (jieba plus every CJK bigram) is essentially the whole cost of indexing, so the original order — build the rows, then compare the hash — made "incremental by file hash" save only the sqlite writes: a no-op rebuild of a 900-file content repo still cost ~35 s, and pre-commit pays that on every commit. The cheap metadata (titles, aliases, the playbook directory) is still recomputed for unchanged files, so the generated pages do not degrade.
- D48 KNOWN ISSUE, deliberately not fixed yet: a row's `id` and `doc` are the file stem, so two files with the same stem in different equipment collapse into one document — in the first real content repo, two equipment each with a `SKILL.md` gave 873 files but 872 distinct docs. Two consequences: `search`'s per-doc cap treats those manuals as one document and makes them share a quota, and `eval` unions doc ids with entry ids when counting hits, so the two can be mixed. Nothing is corrupted — FTS rows are deleted and rewritten by `file`, so incremental bookkeeping stays correct. The fix is to qualify both with the equipment (`<tool>/<stem>`), which changes every row id in the table and therefore the bare ids written in `bench/public/goldset-sunzi.yaml`; it is one cut, to be taken on its own with the gold set updated in the same change, not on the eve of an acceptance run. A third consequence lives in the corpus dimension: `docs{}` in both index.build and check.run is keyed by the derived doc id, so two corpus files deriving the same id collide — index keeps one of them (the clean-beats-raw rule picks the winner) and check merges both texts under one key, which means an anchor sentence from one document would be verified against the other and could pass or fail for the wrong reason. It is latent, not active: the first real content repo has 867 corpus docs and no colliding id. (Recorded against the mechanism that exists. ACCEPT-4's finding ⑤ described this as two `SKILL.md` files overwriting each other in `docs{}` and corrupting anchor verification; that does not hold — a manual is area `manual`, `docs{}` only ever collects area `corpus` (index.build and check.run alike), and anchor verification never reads a manual. The root cause the finding was pointing at is real, and this is where it actually bites.)
- D49 `plug check --contact` step 4 says deny rules are *written*, never that they are *in force*, and the README and gates/README say why: deny rules bind a session whose project root is the content repo, so an agent working from another root edits protected files unimpeded and is stopped only at commit time by pre-commit. Discovered in the first real acceptance run, where an agent rooted outside the content repo edited a protected file and the 18 deny rules were never consulted. The wording matters more than it looks: "deny rules installed" reads as "protected", and that reading is what would let someone drop pre-commit as redundant.
- D50 `plug check --contact`'s MCP probe falls back instead of failing: a dictionary title if the repo has one (unchanged where it does), otherwise a real fragment lifted out of the index, otherwise no assertion on the hit count at all. The original required a dict/*.md Chinese title, so a content repo whose equipment carries no dictionary was told its integration was broken while MCP was in fact healthy — a false alarm in the one check whose whole job is to be trusted after a harness upgrade. A checker that cries wolf on a legal configuration is worse than no checker.
- D51 A rule id may carry a lowercase suffix (P2a, P2b), and finding references to one lives in exactly one place, `shapes.rule_refs()`, used by check (does the id exist?) and by numbers (is the reference real?). Three copies of the pattern had drifted apart, and the failure mode was worse than a wrong answer: with `\d{1,3}` followed by `(?![A-Za-z0-9])`, `P2a` did not match as `P2` — the trailing letter broke the lookahead and the whole reference matched nothing, so it was not misjudged, it was **invisible**. A check that silently sees nothing reports success, which is why the rule count read 26 against a file declaring 28 and nobody noticed until a real Base was installed. Anything that decides whether a reference exists belongs in one function; two copies of a regex is two answers to the same question.
- D52 The files `plug init` generates in a content repo — `.claude/settings.json`, `.mcp.json`, `.codex/config.toml`, `.git/hooks/pre-commit`, the map — carry this machine's absolute paths (D34), and the owner commits them anyway rather than gitignoring them. A content repo is private and lives on one machine, so the record of how it was wired is worth more than portability it will never need; `plug init` is idempotent, so a second machine overwrites them in one command. The alternative, ignoring them, hides the single most useful thing to look at when an integration breaks: what was actually installed, and when.
