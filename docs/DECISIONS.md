# DECISIONS · the places in the spec where I made the call (one line each, with the reason)

- D01 The MCP server is hand-written stdio JSON-RPC (initialize / tools/list / tools/call / ping), not the `mcp` package: the protocol here is four methods, and that is one fewer dependency to drift. First contact talks to it with the same client code.
- D02 A proposal's `base` = the target file's git blob short hash (first 8 chars, same value as `git hash-object`, computed locally, no subprocess); a new file is written `base: new`.
- D03 A proposal's 「改成什么」 must hold one fenced code block = the whole new file (add / replace), or have `retire` on its first line (retire = move to retired/ alongside). A prose-only proposal cannot be landed by a machine, and `plug apply` refuses it and says so.
- D04 An approved proposal moves to `proposals/applied/` (the spec only named pending / rejected / tools; leaving an approved one in pending is wrong and deleting it breaks the trail).
- D05 One FTS5 table is the only retrieval table; two more, `files` (file hashes, for incremental builds) and `meta` (the alias map as JSON, build time, versions), are bookkeeping and are not searched.
- D06 Cleaned-transcript format (the spec had no sample): six `Key: value` header lines + one `====` line + paragraphs starting with `[m:ss]` or `[¶n]`. When one doc id has both raw and clean, only clean is indexed; anchor sentences are grepped in both.
- D07 Doc id order: frontmatter `id` → header `BVID:` / `ID:` → filename stem; series = the prefix before the first separator (｜ | · — - ： :) in the title, verbatim.
- D08 check is split into check.py (findings + report), numbers.py (sync rate) and contact.py (first contact), with eval.py alongside: <=250 lines per file matters more than landing on exactly eight files.
- D09 Agreement is decided as: chosen, normalised, equals verdict, or starts with one of the owner's assent words (同意 / 同 / 按它). Everything else is a disagreement. Who was right afterwards is read from the outcome markers 它对 / 我对 / 说不清.
- D10 "Blind-valid" is verified against git history: in the version where the file was first committed, verdict was set and chosen was empty. Records not yet committed do not count towards the denominator.
- D11 Material shelf life: a material's frontmatter `date` is required, `kind` optional; the number of days comes from that equipment's `ttl_days: {kind: N, default: N}` in plug.yaml (90 by default).
- D12 "New" in "new entry with <3 inbound links" = first committed within 30 days (not yet committed also counts as new).
- D13 `[?]` reconciliation: an equipment may declare `unreviewed: N` in plug.yaml; a mismatch with the actual count is a WARNING. Without the declaration nothing is checked.
- D14 Protected paths default to self/RULES.md · self/facts/** · tools/** (minus **/corpus/**); materials/ is included (the spec says append-only and the writer is the owner). Overridable in plug.yaml `protected:`.
- D15 "Hook has not fired recently" threshold: 30 days, absence included.
- D16 "A warning / diagnostic playbook giving actions aimed at the other party" is a heuristic: a line in the 动作 or 练习 section starting with 让对方 / 叫对方 / 要求对方 / 告诉对方 / 向对方.
- D17 The compaction pin is two-stage: PreCompact computes it, writes `.kb/pin.md` and prints it; SessionStart(compact) runs the same script with `--emit` and hands it back as additionalContext — PreCompact's stdout is not guaranteed to reach the context.
- D18 Mirroring a manual = copying SKILL.md into each pilot's skills directory from plug.yaml (default .claude/skills · .agents/skills), not a directory link; the link approach is documented in pilots/codex instead.
- D19 index.md / INDEX.md generated by index are not git-added by pre-commit; when generated files get committed is the owner's call.
- D20 The generic mount point: `checks/*.py` runs as a subprocess, 60 s limit, with PLUG_ROOT / PLUG_TOOL in the environment; one WARNING per stdout line, exit code 2 = ERROR.
- D21 `file#Lstart-Lend` in a search row uses 1-based line numbers (matching Read and sed); a cleaned transcript's paragraphs carry `[m:ss]` or `[¶n]` as their position.
- D22 Query construction: split on whitespace and punctuation; a Chinese run of <=4 characters becomes a bigram phrase ("责任 任转 转移"), longer runs use jieba words of >=2 characters; latin words are lowercased; everything is OR-ed. Alias expansion uses the same rule.
- D23 The deny template uses `Edit()` only (officially, an Edit rule covers every built-in file-editing tool including Write; a `Write()` rule is never checked); `Read(self/RULES.md)` is never denied, or the pilot cannot read the rules; `Read()` is used only on `.kb/hooks/**`, the stamps the pilot should neither read nor change.
- D24 First contact step ④: pre-commit really runs (PLUG_STAGED stands in for the git index), while deny is only verified by looking for `Edit(…self/RULES.md)` in the settings file — the machine does not start Claude Code itself. Whether deny really blocks under bypass is MANUAL item C1.2.
- D25 "New entry with <3 inbound links" and "orphan entry" only count dictionary entries (concept / method); playbooks are found through INDEX.md, not through links.
- D26 Index freshness is not judged by mtime (two edits in one second are indistinguishable) but by comparing file hashes in the `files` table.
- D27 The corpus is chunked per paragraph (blank-line separated; a cleaned transcript is one paragraph per line with `[m:ss]`), and a paragraph over 800 characters is cut into 600/100 windows; entries / records / materials are one chunk per page (BM25 favours short chunks, so splitting by section would let `## 注` outrank `## 定义`).
- D28 Proposals are indexed into their own scope, `proposals` (invisible to the default `tools` scope, visible with scope=all); otherwise a proposal containing a whole file would outrank the dictionary entry it is about.
- D29 `plug apply` runs `plug index` once more after landing: the proposal has left pending and the playbook directory must stop listing it.
- D30 "Cites earlier records": the 依据 section containing 上次 or `records/` counts as that one of the four elements; the very first record saying 无类似记录 also counts as complete.
- D31 Laying out the one-page report moved from check.py to report.py (check.py was over the hard 250-line limit; check only finds problems, report only formats). The package is 14 files and roughly 1,700 lines, of which about 140 are the mandated header comments; the excess over "~1,000 (<= ~1,300)" is mostly check's ERROR and WARNING classes at 3–6 lines each, and it has not been squeezed further — squeezing makes it unreadable.
- D32 Generated files index.md · playbooks/INDEX.md · the numbers page are committed in the example equipment (they show what the machine produces); `.kb/` and the mirrored skills directories are gitignored.
- D33 Every write uses newline="\n" (on Windows write_text turns LF into CRLF, which changes the base short hash — acceptance item C2.4 is how that was found).
- D34 `plug init`: the hook goes into .git/hooks/pre-commit (git pull leaves it alone; on Windows git runs it with sh; if the owner set core.hooksPath it goes there; anyone else's pre-commit is renamed aside). Claude Code's deny rules and hooks both go into .claude/settings.json (Claude Code does not read .claude/hooks.json). .mcp.json and .codex/config.toml use the current interpreter's absolute path plus `-m entryplug.cli --root <root> mcp`, so nothing depends on `plug` being on PATH. Codex gets a repo-level .codex/hooks.json (the user-level ~/.codex is left alone for the owner to merge). Generated pilot files carry this machine's absolute paths and belong to this machine.
- D35 `search` returning 0/0 no longer stays mute: the tail line names the scope (the default `tools` covers dictionary · playbooks · records; the corpus needs scope=corpus) and when the index was built. With no index the CLI says "run plug index first" and exits 1, and MCP returns isError text. The CLI and MCP were always the same function with the same default scope.
- D36 `plug apply` is the owner's move. If any agent-environment marker is set (CLAUDECODE, CLAUDE_CODE_ENTRYPOINT, CODEX_SANDBOX, … — presence only, values are not inspected) it refuses and prints the owner's two lines. `--dry-run` is allowed for everyone. The escape hatch is `--owner` (or `PLUG_OWNER=1`), because Claude Code's `!` prefix runs in the same environment as the agent's Bash tool, so no environment check can tell an owner keystroke from an agent tool call. That makes this a speed bump with an audit trail, exactly like "do not set KB_APPROVE by hand" — the airtight layer is still pre-commit.
- D37 `.plug-off` at the content repo root turns off only the soft gates: the sortie lock, the compaction pin and the record reminder pass straight through. Deny rules and pre-commit are untouched, so what is protected stays protected in either mode. `plug status` always reports which mode you are in.
- D38 Two free zones, `work/<equipment>/` (products) and `workshop/<equipment>/` (building new equipment): never protected, never walked, never indexed. On top of that, anything under `tools/` belonging to no equipment registered in plug.yaml is not protected either — so deny generation and pre-commit only ever cover `self/` and the registered equipment. Registering an equipment is what makes it protected.
- D39 Equipment = skill: `plug init --link-skills` copies (rather than symlinks) each SKILL.md into the user-level skills directory, so the content repo's absolute path can be stamped into the copy — that stamp is what tells the equipment products belong in `<root>/work/<equipment>/`. Symlinks would carry no stamp and need privileges on Windows. It is a manual trigger, and no user-level MCP server is ever registered: outside the content repo you get the manual, not the Base. `disable-model-invocation: true` in a manual's frontmatter rides along in the copy and also flips Codex's `allow_implicit_invocation` to false.
- D40 The record reminder is a Stop hook and is reminder-level: it never blocks, always exits 0, and emits at most one `systemMessage`. When the session began is taken from the transcript file's creation time, else the previous Stop stamp, else an 8-hour window (PLUG_RECORD_WINDOW). `.plug-off` silences it. This supersedes the earlier "there is no Stop hook" rule, which was written to forbid a *blocking* one.
- D41 `plug status` prints six counted checks (index · Base · AT-Field · berserk lock · sortie lock · equipment bay) plus one informational line for `.plug-off`, which is not counted. The sync rate is simply passed/total. The exit code is nonzero only when the index layer itself is unusable — a degraded lock is loud but does not stop a session. The closing line names the content repo's own directory rather than a hardcoded unit name, so the public machine repo holds nobody's repo name.
- D42 The machine speaks English: comments, docstrings, CLI help and error text, the reports, the README and docs. Content stays in the language it was written in — the Sunzi corpus, dictionary, playbooks and materials, the example Base, and the owner's own words. Shape v1's on-disk vocabulary is data, not prose, and does not move: the section headings (依据 / 最强反证 / 什么会改判 / 改成什么 / 为什么 / 定义 / 观察 / 关系), the markers `[?]` and `[未锚]`, the assent words and the outcome markers, `plug.yaml: language`, and the numbers page's default path `self/数字.md`.
- D43 The owner's copy-paste block lives in three places — the map templates, the footer of every proposal file (check warns with code `footer` when a pending one lacks it), and the pending-proposals section of `plug check`'s report, which prints the real path so the owner can copy it straight out — and its wording is generated in exactly one place, `apply.owner_lines()`. It has two forms, not one: a terminal form (`plug apply <p>` / `--reject`) and a chat form carrying `--owner`. Printing a bare `!`-prefixed approval would hand the owner a command that D36's own gate refuses, since `!` runs in the pilot's environment; `tests/test_apply.py` scans every tracked file for exactly that mistake. `--dry-run` needs no flag anywhere.
- D44 plug.yaml gains an optional `exclude:` glob list that `walk()` honours, so a content repo can keep something out of the index without moving it and without unprotecting it. It is deliberately a visibility switch only — `is_protected` never consults it, so an excluded file is still refused by pre-commit — because the alternative (making one list do both jobs) would let "stop indexing this" quietly mean "stop protecting this". Added for a real content repo whose fact sheet must never become retrievable.
- D45 plug.yaml gains `corpus:` — a list of {path, tool, sub} entries mounting corpus directories that do not live under `tools/<equipment>/corpus/`. walk() hardcoded that layout, so a content repo keeping one shared corpus at its root could not be indexed at all without moving the files, and moving a thousand transcripts to satisfy a directory convention is the tail wagging the dog. `tool` is a label on the rows, `sub` keeps the clean-beats-raw rule, and a declared directory that is not there is a `corpus_path` WARNING rather than a silent skip.
- D46 plug.yaml gains `protect:` — extra globs for the berserk lock — and it is deliberately read by **both** layers: `init.deny_rules` emits a deny rule for each entry and `config.is_protected` hands the same list to pre-commit. The alternative, letting the owner extend one layer only, produces the exact asymmetry found in unit-01, where an equipment's kit directory was refused at commit time but freely editable by the pilot — the worst of both, since the work is lost rather than prevented. `protect:` cannot override the two hard exemptions (free zones, unregistered tools/), because those are the machine's promise that products and drafts stay writable.
- D47 `plug index` compares the file hash **before** generating rows, so an unchanged file is never tokenised again and its chunk count is read back from the table. Tokenising (jieba plus every CJK bigram) is essentially the whole cost of indexing, so the original order — build the rows, then compare the hash — made "incremental by file hash" save only the sqlite writes: a no-op rebuild of a 900-file content repo still cost ~35 s, and pre-commit pays that on every commit. The cheap metadata (titles, aliases, the playbook directory) is still recomputed for unchanged files, so the generated pages do not degrade.
- D48 KNOWN ISSUE, deliberately not fixed yet: a row's `id` and `doc` are the file stem, so two files with the same stem in different equipment collapse into one document — in the first real content repo, two equipment each with a `SKILL.md` gave 873 files but 872 distinct docs. Two consequences: `search`'s per-doc cap treats those manuals as one document and makes them share a quota, and `eval` unions doc ids with entry ids when counting hits, so the two can be mixed. Nothing is corrupted — FTS rows are deleted and rewritten by `file`, so incremental bookkeeping stays correct. The fix is to qualify both with the equipment (`<tool>/<stem>`), which changes every row id in the table and therefore the bare ids written in `bench/public/goldset-sunzi.yaml`; it is one cut, to be taken on its own with the gold set updated in the same change, not on the eve of an acceptance run. A third consequence lives in the corpus dimension: `docs{}` in both index.build and check.run is keyed by the derived doc id, so two corpus files deriving the same id collide — index keeps one of them (the clean-beats-raw rule picks the winner) and check merges both texts under one key, which means an anchor sentence from one document would be verified against the other and could pass or fail for the wrong reason. It is latent, not active: the first real content repo has 867 corpus docs and no colliding id. (Recorded against the mechanism that exists. ACCEPT-4's finding ⑤ described this as two `SKILL.md` files overwriting each other in `docs{}` and corrupting anchor verification; that does not hold — a manual is area `manual`, `docs{}` only ever collects area `corpus` (index.build and check.run alike), and anchor verification never reads a manual. The root cause the finding was pointing at is real, and this is where it actually bites.)
- D49 `plug check --contact` step 4 says deny rules are *written*, never that they are *in force*, and the README and gates/README say why: deny rules bind a session whose project root is the content repo, so an agent working from another root edits protected files unimpeded and is stopped only at commit time by pre-commit. Discovered in the first real acceptance run, where an agent rooted outside the content repo edited a protected file and the 18 deny rules were never consulted. The wording matters more than it looks: "deny rules installed" reads as "protected", and that reading is what would let someone drop pre-commit as redundant.
- D50 `plug check --contact`'s MCP probe falls back instead of failing: a dictionary title if the repo has one (unchanged where it does), otherwise a real fragment lifted out of the index, otherwise no assertion on the hit count at all. The original required a dict/*.md Chinese title, so a content repo whose equipment carries no dictionary was told its integration was broken while MCP was in fact healthy — a false alarm in the one check whose whole job is to be trusted after a harness upgrade. A checker that cries wolf on a legal configuration is worse than no checker.
- D51 A rule id may carry a lowercase suffix (P2a, P2b), and finding references to one lives in exactly one place, `shapes.rule_refs()`, used by check (does the id exist?) and by numbers (is the reference real?). Three copies of the pattern had drifted apart, and the failure mode was worse than a wrong answer: with `\d{1,3}` followed by `(?![A-Za-z0-9])`, `P2a` did not match as `P2` — the trailing letter broke the lookahead and the whole reference matched nothing, so it was not misjudged, it was **invisible**. A check that silently sees nothing reports success, which is why the rule count read 26 against a file declaring 28 and nobody noticed until a real Base was installed. Anything that decides whether a reference exists belongs in one function; two copies of a regex is two answers to the same question.
- D52 The files `plug init` generates in a content repo — `.claude/settings.json`, `.mcp.json`, `.codex/config.toml`, `.git/hooks/pre-commit`, the map — carry this machine's absolute paths (D34), and the owner commits them anyway rather than gitignoring them. A content repo is private and lives on one machine, so the record of how it was wired is worth more than portability it will never need; `plug init` is idempotent, so a second machine overwrites them in one command. The alternative, ignoring them, hides the single most useful thing to look at when an integration breaks: what was actually installed, and when.
- D53 Codex hooks are wired in Codex's own shape. `.codex/hooks.json` is read, but `command` is a single string that Codex splits on whitespace with no quoting, so the Claude form — quoted interpreter and script paths — made it spawn a program whose name contained quote characters, and every Codex hook had reported `Failed` since install. Bare space-separated words work; a path containing a space cannot be expressed, so `plug init` warns rather than writing a hook that will die. The stdin payload is Claude-shaped, so gates/*.py are shared unchanged. **Correction (D56): this entry originally also concluded that a Codex hook cannot veto a tool call. That was wrong.** What remains true is the narrower finding: `exit 2`, `{"continue": false}` and `"async": false` are each ignored by Codex — they are the forms Codex itself marks unsupported. The veto channel exists and is documented in D56.
- D54 Every `--emit` path exits 0, whatever happens. A boot panel and a re-injected compaction pin are diagnostics fed to a SessionStart hook: a degraded layer belongs in the panel as `[NG]`, and even a panel that throws should print one line saying so rather than end the session with a nonzero exit. Only the plain `plug status` (a human is reading it) still returns the index-layer exit code.
- D55 A corrected map template does not reach a repo that already has one, because `plug init` writes CLAUDE.md / AGENTS.md only when absent — they are edited after install, so overwriting them would destroy the owner's work. That trade is right, but it has a cost worth naming: fixing `pilots/codex/AGENTS.md` fixed the next install, while unit-01 went on telling its Codex pilot that outbound actions were «blocked by a hook» after D53 had established they were not. Two mitigations, because documentation alone is what failed here: `plug check` raises `map_claim` when a deployed AGENTS.md still asserts that lock (the one stale claim that makes a pilot read «not blocked» as «allowed»), and README plus pilots/codex/README say plainly that a machine upgrade means diffing your maps against the templates. The general rule: when a fix lives in a template, ask what happens to the copies already deployed — and make the answer mechanical, not a note someone might read.
- D56 The sortie lock blocks on both pilots, through one decision and two exit codes. The decision is `hookSpecificOutput.permissionDecision: "deny"` with a **non-empty** `permissionDecisionReason` — Codex rejects a deny whose reason is empty — printed on stdout. The exit code differs: Claude Code blocks on exit 2 (reason on stderr), while Codex reads that JSON only from a process that exits 0, and a hook that exits 2 has its stdout ignored entirely (tested both ways). `gates/outbound.py` therefore prints the deny JSON always and picks the exit code from the payload: Codex's hook payload carries `turn_id` / `tool_use_id` and Claude Code's does not. The discriminator is the payload and never the environment, because CODEX_* and CLAUDE_CODE_* both leak in when one harness launches the other — observed directly, with Claude Code variables visible inside a Codex hook. The bias is deliberate: mistaking Claude for Codex still blocks, since Claude honours the same deny JSON, while mistaking Codex for Claude would exit 2 and let the call through. Verified live in the real content repo: zero `command_execution` events and the agent reporting that the Sortie lock stopped it.
- D57 «I tried three ways and none worked» is not «the capability does not exist» — and the gap between those two is where D53's wrong conclusion came from. Three careful live experiments (exit 2, `continue:false`, `async:false`) all failed to block, and the inference drawn was that Codex hooks cannot veto. Every one of those three is a form Codex explicitly marks *unsupported* in its own binary, next to the supported one: `PreToolUse hook returned unsupported continue:false`, `unsupported stopReason`, and a deny rejected for arriving `without a non-empty permissionDecisionReason`. Reading the error strings names the supported form directly; black-box probing can only ever rule out the forms you happened to think of. Rule for closed software: before concluding a capability is absent, look for the subject's own vocabulary — its error messages, its serde field names, its enum variants — and only call it absent when the vocabulary has nothing for it. Negative results bound what was tried, not what exists.

- D58 Codex records a `trusted_hash` per hook in `~/.codex/config.toml` under `[hooks.state.'<hooks.json path>:<event>:<group>:<handler>']`, and runs a hook only while that hash still matches the hook as it now stands. Change hooks.json and the hook is **skipped silently** — no error, no notice, and on that side the sortie lock is simply gone. Every `plug init` that rewrites `.codex/hooks.json` therefore disarms Codex until the owner trusts the hooks again, which is the failure mode this project keeps meeting: a control that looks armed and is not. **The hash is Codex's `version_for_toml`.** Take the handler *after Codex normalises it* — absent options dropped, `commandWindows` cleared, an absent `timeout` defaulted to 600 and floored at 1 (SessionEnd and Interrupt instead default to 1 and clamp to 3), an `additionalContextLimit` equal to the 2500 default or set on an event that cannot emit context dropped — wrap it as `{event_name: <snake_case event>, matcher?: …, hooks: [handler]}`, serialise that to JSON with the keys sorted at every level and no spaces, and the answer is `"sha256:" + sha256(utf-8 bytes)`. `config.codex_hooks()` reproduces it: it matches all five hashes Codex itself had written for unit-01, and the two vectors pinned in `test_codex_trust_uses_codex_own_hash_recipe` were cross-checked by hashing the expected canonical JSON by hand. **Correction.** The first version of this entry said the algorithm was undocumented, that the five recorded values had not fallen out of ~2,500 candidate serialisations, and that the check could therefore only detect *change since the last trust decision* — no record, a key set that no longer matches, a hooks.json newer than the config. The brute force was real and it did fail, but the conclusion was D57's mistake a second time: the recipe is written down in Codex's own source (`codex-rs/hooks/src/engine/discovery.rs` `hook_hash`, `codex-rs/config/src/fingerprint.rs` `version_for_toml`), and nobody had read it. Guessing at the outside of a program is not evidence about what is inside it. What the check reports now is what Codex will actually do: which hooks it will run, which it will skip as modified, and which the owner has switched off with `enabled = false` — that last one is silent in exactly the same way. Four surfaces carry it: `plug status` refuses to call the sortie lock armed, `plug check` raises `codex_trust`, `plug check --contact codex` **fails** step 3 rather than reporting a block it cannot deliver, and `plug init` prints a RE-TRUST line whenever it actually changes the file. Re-trusting is one move — open an interactive `codex` in the repo and trust them on its `Hooks need review` screen; `--dangerously-bypass-hook-trust` exists for automation and is not what we want here. Because every rewrite costs the owner that move, **changes to hooks.json are batched**, never dribbled out one at a time.

- D59 A proposal's whole-file block follows CommonMark fencing: the opening run is three or more backticks and only a run at least as long closes it. Before this, `apply.parse_proposal` searched non-greedily for the first closing run, so a target file carrying its own fence was **silently truncated** at that inner fence — everything after it was dropped from the landed content and nothing reported it — and `shapes.sections` flipped a boolean on every fence line, so after an inner fence a `## …` line inside the carried file was read as a proposal heading. Both now track the length of the open run. The alternative was to make the content bend: reformat the target file's own fences into indented blocks so the outer fence stays unique. That was rejected — a refit request has to carry any file byte-for-byte, and a parser limitation that edits the owner's formatting is accommodation running the wrong way. Found by a pilot that hit it twice in one session and worked around it by indenting a real equipment manual.

- D60 The locks are **project-scope only, and that is accepted.** Both layers live inside the content repo — the Claude Code deny rules in `.claude/settings.json`, the hooks in `.claude/settings.json` and `.codex/hooks.json` — so a session started anywhere else (the owner's home directory, another repo, a scratch folder) has neither the sortie lock nor the deny rules over it, and the only thing left between such a session and the content is the `pre-commit` hook in `.git/hooks/`, which stops a commit but not a working-tree edit. A user-level version was designed: hooks registered in `~/.claude/settings.json` and in Codex's user config, self-scoping by checking the payload's `cwd` and path arguments against a registered list of guarded repos, installed only under an explicit `--user-level` and never covertly. The owner **declined it on 2026-09-01**: he means to lock this repo and no more, and accepts the working rule «anything that touches the content repo is done from a session started inside the content repo». It is recorded here as a known, accepted boundary rather than a defect, so that it is not re-proposed as a fix. **The five costs the design put on the table are kept here so that the analysis does not have to be redone if he changes his mind.** (1) It inherits D58 and makes it worse: one edit to a user-level hooks file silently disarms Codex for *every* repo at once instead of one, so `codex_trust` would have to learn to read the user-level trust records too. (2) The scope test is the payload's `cwd` plus string-matching the tool input against the guarded paths, and both can be walked around — `cd` elsewhere first, pass a relative path or a symlink, or read the content into a variable and send that — so **this layer stops what was forgotten, not what was meant**, and any document describing it has to say exactly that or it becomes one more false assurance. (3) Blast radius: every Bash/mcp call in *all* of the owner's projects would spawn one more Python process, roughly 30–80 ms, dampened by hanging it on PreToolUse alone with the matcher narrowed to `Bash|shell|mcp__.*`. (4) Removal has to be as easy as installation (`plug init --user-level --remove`); someone who cannot uninstall it cleanly hand-deletes the config and breaks the project-level layer along with it. (5) The Claude Code half may not lift to user level at all: deny rules are project `permissions`, and whether an `Edit(<content repo path>)` rule in user-level settings binds was **never tested** — by D57 that is to be measured before anything is built on it, not assumed. The recommendation attached to the design was accordingly narrow: build the hook layer only, write «stops the forgotten, not the deliberate» in plain words, and settle the deny half with one real experiment first. Default-allow was deliberate throughout — wrongly blocking the owner's other projects gets the whole layer switched off faster than missing a case does. The consequence for this machine is the reason D58 got the priority it did: because the fence exists in one place only, it must not fail quietly in that place.
- D61 An outbound rule matches the command, not the prose beside it. A shell tool's input carries the command next to a `description` the model wrote about it (Bash: command · description · timeout · run_in_background), and `match(...)` serialised the whole payload — so a call whose *explanation* mentioned an outward tool was refused as an outward action, observed twice in one session, once while the pilot was measuring this very gate. Only the command ever runs, so when `tool_input` has a `command` string that is what a rule sees; a plain string, or a payload shaped differently, still matches on the whole JSON, so nothing stops being seen. This narrows what counts as an *action*, not what counts as outward: literal curl and `git -C … push` are still refused. The limit worth naming: a command that merely *mentions* an outward tool is still a command (`grep -rn curl tools/` remains a hit), because the list cannot tell reading from doing inside the command string — the fix for that class is argv parsing, not a wider regex.
- D62 The hook stamps are deny-write, not deny-read. `plug init` emitted one `Read(.kb/hooks/**)` and no `Edit(...)`, which is backwards on both halves: a pilot that cannot read a stamp cannot check whether a gate actually fired — and `plug check` prints the stamps in its own header anyway, so the denial hid nothing, it only turned verification into hearsay — while writing one is a real attack: forging a stamp silences the "this hook has not fired" warning, and `.kb/` is gitignored so pre-commit never sees the edit. Same lesson as D53/D57 from the other side: before adding a control, ask which direction the damage travels.
- D63 A dot-path can be protected. `is_protected` and `matches` normalised with `lstrip("./")`, which takes a SET of characters rather than a prefix, so it ate the leading dot of every dotted path: `.claude/settings.json` arrived as `claude/settings.json` and could never match a pattern that kept the dot. Every dot-path — .claude/, .codex/, .github/, .env — was silently unprotectable: `plug.yaml` could list it, `plug check` stayed green, and pre-commit let it through. Found the way these things should be found: a content repo added the files that define the locks to `protect:`, then asked `is_protected` whether it had worked, and it said no. `removeprefix("./")` now. The general shape, again: a control that cannot be observed failing is not a control — the fix is cheap, noticing was the whole job.
- D64 `index.md` carries no build time. Three separately reasonable decisions met and guaranteed a permanently dirty working tree: the file is tracked by git, pre-commit rebuilds it on every commit, and D19 deliberately does not `git add` generated files — so every commit ended holding a one-line diff whose only content was the minute it was rebuilt. Harmless until it was not: it blocked a `filter-branch` and had to be discarded by hand mid-operation, and it trains a pilot to read `git status` as noise. The header now names only the counts and the version, so a rebuild over unchanged content produces the same bytes; the build time was never lost, it lives in the index meta (`built_at`) and `plug check` prints it in its header — `index_stale` compares content hashes and never read the file's text. The general shape: a generated file that is committed must be a pure function of its inputs. Anything in it that moves on its own — a clock, a hostname, a run id — is a diff that means nothing, and the cost is paid every single commit.

- D65 The sortie lock makes one decision and exits 0 on both pilots. D56 said Claude Code's PreToolUse payload does not carry `tool_use_id`; it does (the 2.1.257 binary's schema lists it, so do the docs), so the exit-code guess keyed on it sent every real Claude Code call down the exit-0 branch while `contact`, the acceptance script and `test_gate_outbound` only ever exercised the exit-2 branch with hand-written payloads. The guess is gone: the deny JSON on stdout from a process that exits 0 is what both pilots read, verified live on 2026-09-02 (a Bash curl refused in a real Claude Code session, a curl and a git push refused in a real Codex session). The self-tests now probe with the payload shape each pilot really sends. In the same cut the matcher gained the tools the pilots actually expose — Windows Claude Code has a `PowerShell` tool next to Bash, and `Artifact` publishes a page — and `plug init` now rewrites the matcher of an install made earlier, because a widened list that only reaches new installs is not a fix. The example rule reads `git push` by subcommand position (`git stash push` and a commit message saying push are local) and `gh` as a command, not two letters inside a path.
- D66 pre-commit ignores `PLUG_ROOT` and honours `PLUG_STAGED` only outside a real commit. Both were test seams, and both were unconditional: an empty `PLUG_STAGED` made the lock see zero staged files, and `PLUG_ROOT` pointed at another repo made it judge that repo's staged files under that repo's plug.yaml — one environment variable, no `--no-verify`, no trace. git sets `GIT_INDEX_FILE` for every hook it runs, so inside a commit the seam is dead; the root is what `git rev-parse --show-toplevel` says. `KB_APPROVE` stays as the one deliberate override, and `plug status` keeps reporting it.
- D67 pre-commit reads the index with `-z`. With git's default `core.quotePath=true`, `--name-only` printed a non-ASCII path as an octal escape that matched no protected pattern, so every Chinese file name was silently unprotected; this machine only ever saw it work because `~/.gitconfig` had switched quotePath off. `-z` returns raw NUL-separated names whatever the config says; `check.git_added` passes `-c core.quotePath=false` for the same reason.
- D68 The pre-commit hook has to be the real one, and no proposal may target `.git/`. `plug status`, `plug check` and `contact` used `"precommit" in text` to decide the lock was armed; a stub whose only statement was `exit 0` kept the word in a comment and read as armed. `config.hook_ok` now requires exactly one executable line, an `exec` of an existing `gates/precommit.py`. And because `.git/hooks/pre-commit` is untracked and inside the repo, `plug apply` accepted it as a target — the owner could land a stub with his own hands. Targets under `.git/` are refused outright.
- D69 `plug apply` commits with `--only`. A plain `git commit` takes the whole index, and staging is not gated, so a protected edit staged beforehand rode into the approval commit under `KB_APPROVE=1` with a subject naming only the proposal. Only the paths apply itself staged are committed now, listed with `--no-renames` so a moved proposal is a delete plus an add (a rename would hide the old path and leave its deletion staged); anything else stays staged, untouched.
- D70 An equipment check runs only if git tracks it unchanged. `checks/*.py` are globbed from disk and executed with the owner's full environment on every commit and every `plug apply`, while pre-commit only inspects the paths being committed — an untracked or edited script ran without anyone approving it. In a git repo a check must be tracked and clean, otherwise it is skipped with a `tool_check` WARNING that says so; outside git there is nothing to trust against and it runs as before.
- D71 `plug.yaml` is in the default `protected` list. The lock read its own definition from the working tree on every run, and the default list did not cover it, so two ordinary commits — one rewriting `protected:`, one editing the rules — disarmed the berserk lock with no flag and no variable. `init.SELF_PROTECT` had always emitted the deny rule; now both layers agree, and the example plug.yaml says so.
- D72 `.gitattributes` pins LF. Every write in the machine uses `newline="\n"` (D33), but a fresh checkout under `core.autocrlf=true` produced CRLF working files, so the example equipment's blob hashes no longer matched the bases written in its proposals and `test_apply` failed on a clean clone. `* text=auto eol=lf` makes every checkout produce the bytes the hashes were computed from.
- D73 The emitted boot panel says it is for the pilot only. In the first blind A/B of the analysis equipment (2026-09-03, six pairs, two pilots) both pilots copied the SessionStart panel, hook and trust status included, into answers written for the owner, and the blind judge marked every one of them down for it. The panel stays a diagnostic (D53) and injects nothing else; it now ends with one line saying who it is for. The equipment manual carries the matching rule on its side (v1.1: machine state goes into the record, never into the answer).
- D74 The boot panel is for the owner's screen; the pilot gets one line. `plug status --emit` now sends the whole panel as `systemMessage` (Claude Code shows it, the model never sees it) and only `entry plug boot: <verdict line> · <every [NG] line>` as `additionalContext`. The panel was a dozen lines of measured facts in every session's context, and the blind tests showed pilots quoting it; a degraded layer still reaches the pilot through the [NG] lines. Codex ignores `systemMessage`, so on that side the panel is what `plug status` prints by hand and the pilot gets the same one line.
- D75 pre-commit refuses and does nothing else. The hook used to rebuild the index and run the whole check-up (equipment checks and the numbers page included) on every commit, so every commit paid seconds, ran code on the owner's behalf, and left `self/数字.md` dirty by one line. Now it refuses a protected path without KB_APPROVE (the berserk lock) and refuses a staged record or proposal whose shape is broken; the check-up is `plug check`, run when the owner wants it, and the index rebuilds itself on read (D76).
- D76 The index rebuilds on read. `plug search` and the MCP search test staleness first — a content file newer than the last build or a different number of files, no hashing — and rebuild incrementally before answering, so `plug index` stops being a ritual the pilot has to remember. `plug status` never writes, so its probe searches without the rebuild.
- D77 The record reminder fires once per session. The Stop hook ran at the end of every turn and nudged every time no record had been written, which read as nagging; it now remembers its own stamp and stays silent after the first nudge of a session (the transcript's start; a window when there is no transcript).
